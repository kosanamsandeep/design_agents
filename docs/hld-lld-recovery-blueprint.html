Research synthesis · October 2026

Recovering HLD & LLD from an existing codebase — and using them to migrate

What the tool ecosystem actually does well, what it does not, and a buildable design for an enterprise pipeline: deterministic evidence first, LLM synthesis second, independent verification always — shipped as one governed agent bundle.

Scope: multi-language codebases from ~100k to 10M+ LOC; as-is recovery, to-be design, and dependency-ordered migration.

✓ Verified 27 Oct 2026 3 research streams + packaging audit Single-file · printable · downloadable ✓ Diagrams embedded as SVG · works offline
The one-sentence verdict No open-source project does archaeology → HLD + LLD → migration end-to-end. Use license-cleared evidence engines, build the synthesis layer, and treat migration as a separate discipline with deterministic engines and independent oracles.

  1. Split the problem. Recovery (as-is) is not design (to-be) and neither is the migration delta. Different tools, different gates.
  2. Deterministic first. Symbols, calls, routes, imports, configs, and schema are provable. Never ask an LLM to infer what a parser can prove.
  3. Partition by path, not by graph communities. CodeBoarding tried Leiden communities and discarded them; directory/qualified-name leaves scored far better. Use edges to validate boundaries, not to invent them.
  4. Hierarchy beats graph for writing; graph wins for finding. Raw-text map-reduce was near parity with graph-RAG on synthesis, but graphs dominate localization (92.7%) and blast radius.
  5. Evidence or nothing. Every diagram element cites file:line with a confidence label. A different model refutes claims. Same-model self-review is measurably unsafe.
  6. Migration is a separate engine. Agents plan and handle residue; deterministic tools do bulk edits; characterization, contract, and architecture-diff gates verify. “Tests pass” is not an oracle.

What this blueprint is

  • An evidence-grounded recovery pipeline
  • A migration planner fed by that model
  • A packaged, versioned, governable agent bundle
  • An eval harness with published metrics

What it is not

  • A documentation wiki generator
  • A chatbot over the repository
  • An autonomous mass-editor
  • A substitute for maintainer sign-off on boundaries

01 The three problems people conflate

“Generate HLD and LLD from the codebase” bundles three jobs with different inputs, different tools, and different definitions of done.

Recovery produces evidence; design produces intent; delta is the difference. Only the delta is a migration plan.

Diagram source (Mermaid)

    B --> C["② DESIGN<br/>to-be C4 model"]
    C --> D["③ DELTA<br/>dependency-ordered slices"]
    D --> E["Verified change<br/>canary / strangler"]
    B -.->|"evidence"| C
    D -.->|"reflexion check"| B
Problem Question it answers Primary method Definition of done Owner
① Recovery What is actually here, and how does it run? Static analysis, graph, LLM naming/synthesis, evidence Maintainer agrees boundaries; evidence coverage high; gaps listed Archaeology lead + domain maintainer
② Design What should it become? Human intent + target C4 model + mapping rules Target model approved; NFRs and ownership explicit Architect + product
③ Delta In what order do we change it without breaking it? Semantic diff, topological ordering, blast radius, risk Ordered slices with acceptance criteria and rollback Migration lead + SRE
The classic failure Teams ask one agent to do all three in one pass. The output is a plausible HLD, a shallow LLD, and a migration plan with no dependency order — impossible to verify and dangerous to execute.

02 Reality check: what is provable, and what is not

Context math

Code averages roughly 7.5–10 tokens per line. A 1M-token window therefore covers only about 100k–125k LOC — not a million. Whole-repo prompting is a small-repo technique.

Repo sizeApprox tokensViable strategy
10k LOC75k–100kWhole-repo prompting + strong citations
100k LOC0.75M–1MWhole-repo only with a big window; prefer indexing
1M LOC7.5M–10MIndex + hierarchical map-reduce (mandatory)
10M LOC75M–100MGraph + partition + incremental hashes; never send whole files en masse

Boundary recovery is genuinely approximate

Architecture-recovery research measures clustering quality with MoJoFM (0–100). Across established techniques the numbers are honest, not flattering:

TechniqueMoJoFM — BashMoJoFM — Chromium (~9.7M LOC)Read
ACDC5970–73Best general baseline
Bunch-SAHC5870Similar quality, slower
WCA4390 (module-level)Strong on large systems with good module structure
ARC4045Weaker; scales
LIMBO2823–85High variance

The source study concludes that overall accuracy is low for all recovery techniques. Symbol dependencies outperform include dependencies, and ACDC/Bunch/WCA/ARC scale to ~10M LOC. The implication is a design rule, not a reason to give up: treat recovered boundaries as hypotheses for a maintainer to confirm.

What static analysis cannot see

  • Dynamic dispatch — DI containers, reflection, service locators, plugin registries, event buses. The graph sees the registration, not always the call.
  • Runtime topology — what actually runs, with which env vars, replicas, feature flags, and network policies.
  • Cross-language edges — Python worker triggered by a Kafka topic produced in Java; a Go gateway calling a .NET service.
  • Business intent — which modules are one bounded context because of domain language, not directory layout.
Mitigation Join the static graph with deployment manifests, config, message schemas, and optional runtime traces. Mark anything not directly observed as inferred or hypothesis. Never present inference as fact.

Long-context is not free

“Lost in the Middle” measures a U-shaped accuracy curve: evidence in the middle of a long context degrades by roughly 15–20 points versus the edges. Prefer several focused 8k–50k-token calls over one giant prompt, and place the graph slice and entry points at the edges of each call.

04 What the research changed

Five assumptions that did not survive contact with the evidence — including one I made earlier in this project.

Earlier assumptionWhat the evidence saysDesign change
Cluster into bounded contexts with graph communities (Leiden) CodeBoarding tried Leiden on the call graph and discarded it. Path-based file leaves scored 0.34→0.94 (Beacon) and 0.67→1.00 (eShop) against maintainer rulers. Path-first partitioning. Directory + build unit + deploy unit define leaves; edges validate coupling.
Graph-RAG improves synthesis GraphRAG’s community map-reduce beat vector RAG on comprehensiveness 72–83% of the time — but a plain raw-text map-reduce baseline was near parity. The hierarchy did most of the work. Graph for localization (92.7% file-level) and blast radius; hierarchical summarization for writing.
One strong architect agent can write the HLD ArchAgent’s file summaries → token groups → partial diagrams → merge reached F1 0.966 vs 0.860 for DeepWiki. DeepWiki freezes an 8–12 page outline before parallel page generation. Freeze outline.json, then fan out. Bounded calls, 10% overlap, shared IDs.
Recovery tools produce the real architecture MoJoFM is 43–90; the source study says overall accuracy is low for all techniques. Boundaries are hypotheses. Confidence labels + maintainer sign-off. No diagram ships as “truth”.
More agents produce better results Agentless (localize → repair, no swarm) scored 27.33% on SWE-bench Lite at $0.34/issue. LocAgent’s graph beat agent wandering on cost. Seven narrow roles in a pipeline, not a swarm; only one has write access.
Code review and tests catch structural damage In a reported study, lint/type checks caught 2 of 67 structural defects; tests/SAST caught 0. Cross-cutting tasks fail ~44.6% vs 13–16% single-file. Architecture-diff gate + contract/schema tests + independent verifier.

The reflexion model — the missing migration primitive

Reflexion analysis (Murphy et al., TSE 2001) is the established “as-designed vs as-implemented” technique: a human supplies a hypothesized architecture plus mapping rules; the tool compares it with extracted source relations and reports convergences and divergences, iteratively. It is exactly what a migration needs.

Reflexion is conformance checking, not automatic recovery. Use it before a migration to size the gap, and after every slice as a CI gate.

The evidence rule

Every element in the HLD and LLD carries provenance and a confidence label. This is the schema the verifier enforces:

{
  "id": "svc:billing",
  "type": "container",
  "name": "Billing Service",
  "confidence": "inferred",              // extracted | inferred | hypothesis
  "evidence": [
    {"file": "deploy/k8s/billing.yaml", "lines": "12-40"},
    {"file": "services/billing/src/main.py", "lines": "1-80"}
  ],
  "edges": [
    {"to": "db:orders", "kind": "writes", "confidence": "extracted",
     "evidence": [{"file": "services/billing/src/repo.py", "lines": "88-104"}]}
  ],
  "unknowns": [
    "ownership: unclear whether orders reads invoices directly or via the API"
  ]
}
Delete uncited claims The critic does not “improve” an unsupported claim — it removes it and records it as an unknown. An HLD with honest gaps is more valuable than a complete-looking fiction.

Context hygiene rules

  • Read-only recovery phase. No agent gets write tools before S6.
  • Only migration-worker writes, in an isolated worktree, one slice per PR.
  • Critic and verifier run on a different model family from the synthesizer.
  • No agent reads the whole repo. It reads its graph slice, its file list, and the outline.
  • Artifacts go to disk; agents return ≤2k-token summaries and paths.
  • Every tool call is logged with commit SHA + tool version for reproducibility.
  • No self-approval: a worker cannot be the verifier of its own output.
  • Budgets are enforced by the harness, not requested in the prompt.

Deterministic vs agent — the division of labour

Deterministic engine

  • Mechanical API/framework upgrades
  • Import/package moves, renames
  • Schema and config rewrites
  • Impact scan + CI guardrail
  • Architecture-diff verification

Agent

  • Choose the recipe / tool per slice
  • Handle semantic residue a rule cannot express
  • Repair call sites after a move
  • Explain diffs and risk
  • Propose the next slice when blocked

    "invoice.total == sum(line_items.amount)",
    "no cross-context table writes"
  ],
  "edits": [
    {"engine": "ast-grep", "rule": "no-direct-orders-db", "scope": "services/billing/**"}
  ],
  "acceptance": [
    "characterization suite green",
    "contract diff empty",
    "reflexion: zero divergences for this context"
  ],
  "rollback": "feature flag billing_v2; revert PR; no data migration in this slice"
}

Gates that must be automated

  1. Characterization gate — behavior frozen before the slice, compared after.
  2. Contract gate — OpenAPI/proto/GraphQL/schema diff is empty or explicitly approved.
  3. Architecture-diff gate — reflexion report: intended convergence, no new divergence.
  4. Invariant gate — repo-wide rules (no cross-context writes, layering, dependency direction).
  5. Canary gate — error rate, latency, and business KPIs within budget.
  6. Rollback rehearsal — the slice is only done when rollback has been exercised.
Never let “tests pass” end the conversation Tests are necessary evidence, not sufficient. The study above found tests and SAST caught zero of 67 structural defects. Structural validity needs a structural oracle.

Pilot repo selection

  • Business-critical enough to matter, bounded enough to finish (20k–200k LOC).
  • One dominant language; a maintainer willing to spend 2–4 hours reviewing boundaries.

Cost model (shape, not price)

LLM prices change; model the drivers, not a dollar figure:

  • Facts + graph: CPU-bound, one-time + incremental. Cheapest stage.
  • HLD: ~50–200 bounded calls over summaries and graph slices.
  • LLD: contexts × calls per context; the dominant token cost.
  • Critic: roughly 1.5–2× the synthesis tokens (CoVe-style verification cost).
  • Incremental runs: file hashes + cached summaries; target ≤20% of full cost.
  • Levers: cheap model for scouting/summarizing, frontier only for synthesis, prompt caching, fan-out concurrency caps, and refusing to re-summarize unchanged files.

09 Skills, agents, and the agent package manager

The user-facing question is “how do skills, agents, and APM tie together?” The short answer: skills are the method, agents are the workers, plugins are the shipping container, the marketplace is the registry, and managed policy is the trust layer. Each is separately versioned and separately governed.

There is no mandatory central registry Claude Code discovers plugins through marketplaces: git repositories, hosted marketplace.json URLs, local directories, archives, or npm sources. That is precisely why an internal marketplace is the right enterprise control point — it is the one catalog your organisation approves, pins, and provisions from.

Portability rule The Agent Skills format was donated to the Agentic AI Foundation (Linux Foundation) on 22 Oct 2026 and is implemented by 70+ agent platforms. Portable SKILL.md may only use name, description, license, compatibility, metadata, and allowed-tools. Anything clever (context, agent, paths, hooks, model overrides) is harness-specific and belongs in the agent layer.

Lifecycle and versioning

  1. Author in the marketplace repo; keep skills spec-only.
  2. Validate with claude plugin validate --strict in CI.
  3. Evaluate against golden repos; block promotion on regression.
  4. Tag a semver release (claude plugin tag) and pin the SHA.
  5. Pilot with a local marketplace or --plugin-dir.
  6. Publish to the internal marketplace (stable + beta refs).
  7. Provision via extraKnownMarketplaces / enabledPlugins; managed settings enforce the rest.
  8. Observe drift, eval scores, and install inventory; roll back by pinning the previous version.

Trust and supply chain

A plugin is executable code Hooks and monitors run shell commands with your full user privileges, outside the sandbox. MCP/LSP servers start processes. bin/ is added to the Bash tool PATH while enabled. Auto-update can change files you already reviewed.
  • Allowlist marketplaces; block the rest in managed settings.
  • Pin GitHub/git sources to a full 40-character SHA; pin archives by sha256.
  • Review hooks/hooks.json, .mcp.json, and bin/ before approving a version.
  • Use allowManagedHooksOnly where hooks must be centrally controlled.
  • Keep recovery agents read-only; the only writer is the migration worker, and it runs in an isolated worktree.
  • Store artifacts with commit SHA and tool versions so any conclusion is reproducible.

Anti-patterns to ban explicitly

  1. Whole-repo prompt — fails above ~100k LOC, no provenance.
  2. Community-first clustering — validated failure in production tooling.
  3. One giant architect agent — no coverage guarantee, no isolation.
  4. Agent performs bulk edits — measured drift and patchwork.
  5. Same-model review — misses ~31.7% of behavior changes.
  6. “Tests pass” as the only oracle — zero structural defects caught in the cited study.
  7. Recovered HLD treated as truth — accuracy is approximate; humans sign off.
  8. Free-text Mermaid — render from the structured model and validate it.
  9. No eval set — you cannot tell improvement from prettier diagrams.
  10. Skip characterization tests — migration becomes unverifiable.

11 One-page cheat sheet

Seven stages

  1. Facts — manifests, IaC, DB, APIs
  2. Graph — symbols, calls, routes, data
  3. HLD — path leaves → C4 + outline
  4. LLD — fan-out per context
  5. Verify — evidence + independent critic
  6. Plan — reflexion + topo slices
  7. Execute — deterministic bulk + residue

Five artifacts

  1. repo.facts.json
  2. code.graph.json
  3. outline.json + c4.model.json
  4. lld/<context>.json
  5. migration.plan.json

Always

  • Deterministic facts before LLM synthesis
  • Path-first partition, edges validate
  • file:line + confidence on every claim
  • Different model verifies
  • Freeze the outline before fan-out
  • Characterization + contract + arch-diff gates

Never

  • Prompt the whole repo
  • Cluster components from Leiden alone
  • Let the synthesizer approve itself
  • Let an agent do the bulk edit
  • Treat “tests pass” as sufficient
  • Ship an unevidenced diagram

The 12 design rules

  1. Index structure deterministically before asking a model anything.
  2. Partition by directory/build/deploy; validate with graph edges.
  3. Freeze the outline/TOC before parallel generation.
  4. Summarise hierarchically, file → subsystem → system, with 10% overlap.
  5. Write LLD from exact symbols and call edges, with one shared ID space.
  6. Require file:line evidence and an explicit confidence label.
  7. Run an independent verifier; delete unsupported claims.
  8. Render diagrams from the model, then validate them.
  9. Go incremental by file hash; never serve stale indexes silently.
  10. Evaluate with F1 and MoJoFM on maintainer-labeled repos.
  11. Get human sign-off on HLD boundaries.
  12. Reflexion-check as-is against to-be before and after every slice.

Glossary

HLD
High-level design: services, data stores, runtime flows, NFRs.
LLD
Low-level design: classes/types, call sequences, states, invariants, seams.
Evidence
A file:line pointer supporting a claim, with a confidence label.
Reflexion
Conformance check between a hypothesized architecture and extracted source relations.
MoJoFM
0–100 metric for how close a recovered partition is to a reference partition.
Blast radius
The set of modules reachable from a change; used for risk and slice ordering.
Seam
A place where behaviour can be changed or extracted with minimal coupling.
Characterization test
A test that freezes existing behavior before a refactor.
APM
Agent package manager: marketplace + plugin bundle + versioning + policy.
AAIF
Agentic AI Foundation (Linux Foundation), steward of Agent Skills, MCP, A2A, and AGENTS.md.
Map-reduce fan-out
Generate per-context artifacts independently, then merge under a frozen outline.
Drift
Code and its recovered model diverge over time; detected by incremental re-index and CI.
