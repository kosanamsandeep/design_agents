01 What changed

The licence gate was doing the work of a procurement policy. Internal-only use replaces it with bank intake + SBOM; maturity becomes the tie-breaker.

Diagram source (Mermaid) 
flowchart LR
    A["Old premise<br/>redistributable bundle"] --> B["Hard licence gate<br/>MIT / Apache only"]
    B --> C["Exotic graph-first stack<br/>Graphify + CodeGraph + CodeBoarding"]
    D["New premise<br/>internal-only use"] --> E["Bank OSS intake + SBOM<br/>no redistribution or service"]
    E --> F["Mature baseline<br/>SCIP · tree-sitter · Serena · Joern · Semgrep"]
    F --> G["Bake-off optional engines<br/>Graphify · CodeGraph · CodeBoarding"]

What opens up

  • GPL/LGPL/MPL/EPL tools — Serena, Semgrep OSS, pyreverse, PlantUML, EvoSuite, D2, Graphviz — internally, unmodified, subject to bank policy.
  • OpenRewrite MSAL recipes — migrate-java, spring, testing-frameworks, static-analysis, logging — usable internally; check contractors/vendors as third parties.
  • Mature tooling — SCIP, tree-sitter, Serena, Joern, Semgrep, Structurizr, Mermaid, PlantUML.

What stays blocked or needs review

  • Moderne Proprietary — java-security, kubernetes, sql, Spring/Hibernate sets: commercial contract.
  • CodeQL CLI — private commercial code likely needs GitHub Advanced Security; verify.
  • AGPL (TruffleHog) — often banned by bank policy; gitleaks avoids the question.
  • Sourcegraph / AWS Transform — third-party risk review.
What does not change Evidence-or-nothing, the independent critic, golden-repo evaluation, human sign-off on boundaries, and the migration gates. Those are about correctness, not licensing.

02 Revised decision

The baseline is now the mature toolchain. The graph engines are optional extras that are actively tested in the bake-off; they must beat the baseline on a measured metric to be promoted, and they are no longer the foundation.

Mature baseline first; optional engines must show a measured, non-overlapping win before they are enabled for a repository.

Graphify and CodeGraph are not dropped — they are candidates, not baseline The baseline deliberately excludes them so the bake-off measures replacement, not the benefit of combining engines. Both are tested in Phase 3 (week 6) as separate experiments. If either wins on a measured metric, it is promoted for the repo profile where it wins; if not, it is dropped.

CodeGraph Call paths, blast radius, framework routes for LLD and migration Measured flow-recall or blast-radius precision gain Gain only on migration-heavy repos → enable there; no gain or maintainer risk unacceptable → drop

03b Language coverage — what “all languages” really means

The evidence schema is language-neutral. The adapters are not. HLD is mostly language-agnostic; LLD depth is gated by the per-language symbol/indexer and framework profile.

TierWhat you getInitial languagesRequirements
A · Full HLD + LLD Classes/types, call paths, flows, states, seams, invariants, evidence Java/Kotlin/Scala, Python, TypeScript/JavaScript, Go, Ruby, C/C++, C# SCIP indexer + tree-sitter + framework profile + golden repo
B · HLD + structural LLD Modules, files, imports, routes, syntax-level calls; no precise type/state model Rust, PHP, Swift, Elixir, and others with a good tree-sitter grammar tree-sitter (or LSP) + manifests; call/type edges marked inferred
C · HLD inventory only Services, deploy units, data stores, contracts; no code-level LLD Obscure languages, DSLs, low-code platforms Manifests, IaC, API/queue contracts
Out of scope Declared, not silently degraded COBOL/PL-I, ABAP, RPG, mainframe until a specialized tool is procured Explicit decision

HLD vs LLD by tier

CapabilityTier ATier BTier C
Services, deploy units, data storesYesYesYes
Runtime flows across servicesYes, with contracts/tracesCoarseNo
Classes / types / interfacesYesSyntax-levelNo
Call paths / blast radiusYesPartial, inferredNo
State machinesYes, inferred + confirmedHeuristicNo
Seams / invariantsYesLimitedNo

Cross-language edges — HTTP, RPC, message topics — come from contracts and runtime traces, not from either language's LLD. LLD is always per language; the HLD joins services across languages. Dynamic languages (Python, Ruby, JavaScript) and DI/reflection in Java/C# mean static call graphs can be incomplete; runtime traces are mandatory for critical flows.

Adding a language

  1. Pick the indexer: official SCIP indexer, LSP, or tree-sitter fallback.
  2. Add a tree-sitter query pack for calls, imports, inheritance, and routes.
  3. Write canonicalization rules for qualified names, overloads, and generated names.
  4. Add a framework profile: routes, ORM, DI, queues, state idioms.
  5. Add fixtures and a small maintainer-labeled repo.
  6. Set the tier and eval thresholds; declare unsupported capabilities.

COBOL is the one that changes the plan Lloyds publicly describes roughly 200 COBOL applications, with active mainframe hiring across payments and core banking. There is no official SCIP indexer for COBOL. Under this plan, COBOL gets HLD inventory only (services, jobs, transactions, data stores) from mainframe metadata; full LLD requires a specialized tool (e.g. IBM ADDI, AWS Transform for COBOL, OpenText/Micro Focus) or a dedicated COBOL adapter. Align with the bank's existing COBOL modernization effort rather than duplicating it.
React is not a language React/Next.js is TypeScript/JavaScript with a front-end profile: components, routes, props/state, and API calls. The HLD/LLD shape is different from backend services; do not assume the backend LLD template fits unchanged.
We do not promise “all languages” We promise a coverage matrix: a language is full, structural, inventory-only, or out of scope, and the output says which. Unsupported languages fail closed with coverage and unknowns — never silent degradation.
Choose the pilot language from the estate, not the catalogue Start with the highest-volume Tier A language in the bank. The first vertical slice proves the pipeline on that language; other languages are added by estate priority.

Open decisions

  1. Internal-use scope: contractors/vendors, managed service, redistribution — confirm in writing.
  2. Migration route: MSAL recipes internally, own recipes on Apache core, or Moderne procurement.
  3. Pilot and golden repos: names, owners, labelers, commit SHAs.
  4. Model endpoint: approved provider/model, data handling, retention.
  5. Runtime traces: tool choice for critical flows (OpenTelemetry/eBPF/other) or declared out of scope.
  6. PlantUML: keep for richer diagrams or stay Mermaid-only.
  7. COBOL/mainframe scope: HLD inventory only, specialized tool procurement, or a dedicated adapter; align with the existing modernization programme.
  8. SQL/PL-SQL depth: extend the schema for stored procedures, triggers, and views, or declare data-logic LLD out of scope.
  9. React/TypeScript profile: decide the front-end LLD shape (components, routes, API calls) and whether it is in the first three languages.

11 Exit criteria — what “live” means

  1. Intake and legal pass on the baseline, including internal-use attestation, SBOM, notices, and contractor review.
  2. Schema v1 frozen after SCIP and tree-sitter adapters produce consistent, auditable records on the pilot.
  3. Golden-repo targets met on all three repos, including the messy one: evidence coverage, boundary F1, flow recall, unsupported claims with recall.
  4. Bake-off decisions measured — each retained optional tool has a non-overlapping win; the rest are removed.
  5. Model-risk sign-off and approved model endpoint in place.
  6. One migration slice completes end to end through characterization, contract, architecture diff, canary, and rollback.
  7. Operational readiness — runbooks, eval regression gate, on-call ownership, second team onboarded.
No production gate is passed by a document Every criterion above requires evidence: a signed attestation, a passing contract suite, a measured scorecard, a signed-off HLD, or a completed slice with rollback.
